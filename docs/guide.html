1The 60-second pitch

sudo is an Android app that keeps you current in tech and AI. It pulls news only from established outlets and official AI-lab blogs, summarises each story in about 50 words on the phone with a small model I trained, tracks new and rising AI/ML/data-science terms (the "Skills Radar"), and lists jobs and internships matched against your resume — with a one-tap assisted apply and an application tracker.

What makes it different
  • It can't make things up. Summaries are the publisher's own sentences, chosen by an on-device model — nothing is generated. Every card links to its source.
  • Nothing is hardcoded. The Skills Radar mines new terms from live research and verifies each one against independent sources (OpenAlex publication history + arXiv activity) before showing it.
  • It proves it. A live "truth audit" test re-checks headlines, links, summaries, job pages, trending items and radar terms against the original sources.
  • No backend. Everything runs on the phone; there is no server to run or pay for.

2What the app does

⚡ Tech Pulse

Tech news from The Verge, Ars Technica, TechCrunch, Wired, Engadget, BBC, The Register, MIT Technology Review, Rest of World and The Hacker News. Topic chips (AI, Security, Startups, Gadgets…), a hero story, ~50-word summaries, "+N outlets" when several outlets cover the same story.

✦ AI & Data

Official lab blogs (Google AI, Google Research, DeepMind, OpenAI, Hugging Face, NVIDIA, AWS ML, MIT News AI), AI desks (Ars AI, TechCrunch AI, The Decoder), data-science (KDnuggets, Towards Data Science) and arXiv cs.LG / cs.CL. Plus Skills Radar and Trending now.

◎ Skills Radar

A permanent, month-by-month record of new and rising AI/ML/DS terms and tools. Each has a quoted "what it is", "where it's used", the numbers behind it and its sources.

▤ Trending now

Hugging Face trending models, Hugging Face Daily Papers (by upvotes) and rising AI/ML repos on GitHub — straight from their live sources.

🚀 Rising on GitHub

The 15 repos gaining stars fastest, with a direct link, the author's description and a quoted README paragraph. All / AI/ML / For you filters; updates every 3rd morning and keeps the list unchanged when nothing new makes it.

💼 Jobs & Internships

Remote and on-site roles; filters for internships, full-time, remote, on-site, near me and "direct from employer"; a match score and skill gaps computed against your resume; a scam filter.

🚀 Assisted apply + Tracker

Tap-to-copy details, an optional tailored cover letter, opens the employer's real form; you submit. Tracker: Saved → Applied → Interview → Offer / Rejected with a 7-day follow-up reminder.

🔔 Alerts & widget

Notifications when a headline or new job mentions your keywords; a home-screen headlines widget (Glance).

🔖 Saved & offline

Bookmarked stories are stored locally and never expire. Launch intro (~2.4 s), light/dark themes, onboarding.
Why "assisted apply" instead of auto-apply The original idea was an app that fills and submits applications automatically. That was rejected on purpose: LinkedIn/Indeed terms forbid automated applications (accounts get banned), every employer uses a different system (Workday, Greenhouse, Lever…) with CAPTCHAs and custom questions — so a bot would fail silently and often. Assisted apply keeps the speed (everything ready to paste) while the user stays in control and nothing is sent without review.

3Design principles

  1. Trust first. Only established sources. Every item shows where it came from and links to the original. Undated, future-dated, off-site and promotional items are rejected (Section 14).
  2. Extract, don't generate. The default summaries and all radar explanations are verbatim quotes. Generated text (Gemini) is optional, labelled, and must pass a grounding check that rejects any number, name or claim not present in the sources.
  3. No hardcoded content. Terms, trends and acronym meanings are learned from live data. What is fixed is the list of trusted outlets — deliberately, because it's the trust anchor.
  4. Never guess. If a verification source is unreachable or rate-limited, the radar pauses and says so instead of showing unverified results.
  5. On-device and private. No server, no analytics, no account. Keys and your resume stay on the phone.
  6. Honest labels. "AI summary" vs "Key sentences · on-device" vs "Excerpt"; "live on careers page" instead of "posted 31 months ago"; "took off in 2024".
  7. Prove it with tests. A live audit checks the app's output against reality, not just that the code runs.

Why native Kotlin and not Flutter / React Native?

The app relies heavily on Android-specific capabilities: WorkManager background refresh, battery-optimisation exemption, notifications, a home-screen widget, Custom Tabs and a file provider for the resume. Native Kotlin gives first-class access to all of them, the best performance for long scrolling lists, and the ability to run the exact same parsing/ML code in fast JVM unit tests. The trade-off is no iOS version.

Why no backend?

A server would have to fetch, store and serve content — cost, maintenance and a privacy surface. Every source used is public and free, so the phone can fetch directly. The cost of this choice is that each phone does its own work (handled by the background worker, memory budget and rate-limit handling described later).

5Architecture

Key patterns

  • Repository pattern: each feature's data logic (fetch, clean, verify, store) lives in a repository; the UI only observes the database.
  • Single source of truth: network results are written to Room; screens observe Room Flows. That's why the app shows cached data instantly and works offline.
  • Manual dependency injection: one AppContainer object builds everything. For an app this size, Hilt/Koin would add complexity without benefit; tests pass an in-memory DB into the container.
  • Pure, testable core: NewsFilter, RssParser, TermMiner, ExtractiveSummarizer, Skills have no Android dependencies, so they are unit-tested on the JVM.

7The news pipeline

  1. Fetch. All 25 feeds are downloaded in parallel (a semaphore limits it to 8 at once). A failing feed never blocks the others.
  2. Filter (NewsFilter.reject): an item must have a real publish date, no more than 2 hours in the future (clock-skew tolerance) and not older than 72 hours; must link to the same publisher as the feed (compared by "brand", e.g. bbc for bbc.com and bbc.co.uk, also accepting the site the feed declares in its own <link>); must be http(s); must have a headline; must not be commerce (promo codes, coupons, deals, ticket and event promos).
  3. Dedupe. ID = a SHA-1 hash (first 20 hex characters) of section + canonical URL (tracking parameters like utm_ removed). The same story can exist in both Tech and AI tabs.
  4. Enrich. Of the 80 newest new items, the first 40 whose feed text is short (<400 chars) or that have no image get their article page fetched (6 at a time; arXiv is skipped) and Jsoup extracts the body paragraphs and the og:image.
  5. Summarise. The on-device extractive model picks the key sentences (Section 11). If the text is too thin, the publisher's excerpt is shown, labelled "Excerpt". If the user enabled Gemini, up to 20 recent items per refresh are rewritten in batches of 10 and labelled "AI summary".
  6. Cluster. Headlines are tokenised; two stories in the same section within 48 h are the same story if Jaccard ≥ 0.45, or ≥4 shared words with ≥60% overlap. arXiv papers only merge on identical titles (different papers often share vocabulary).
  7. Store & alert. Inserted into Room; keyword alerts sent (never on the very first sync); stories older than 7 days are pruned unless bookmarked.

Topics (AI, Security, Startups, …) come from keyword rules, optionally overridden by Gemini. Clustering is a trust feature: "covered by 4 outlets" is a signal that a story is real.

  • Tech-role filter: "strong" title words (engineer, developer, scientist, data, ML…) always qualify; "weak" ones (AI, research, analyst…) only if the title isn't clearly non-tech (sales, recruiter, marketing…).
  • Dedupe: same title + company + location across sources → the employer's own posting wins.
  • Freshness: job-site listings older than 45 days are dropped; employer-board listings are kept while the company still lists them (labelled "live on careers page"); at most 120 tech roles are taken per company board. Listings not seen at their source for 3 days are deleted.
  • Large responses: some boards return 10–15 MB of JSON (OpenAI's ~14.6 MB). They are decoded straight from the network stream into small typed models (kotlinx.serialization decodeFromStream) instead of building a full JSON tree, to stay within phone memory.
  • Sync cadence: at most hourly (the 15-minute worker skips jobs if the last sync was <55 min ago); pull-to-refresh forces it.

Match score and skill gaps

A fixed vocabulary of 82 canonical skills with aliases (e.g. k8s → Kubernetes, sklearn → scikit-learn) is matched with word-boundary regexes against the job text and the user's skills. Score = matched ÷ min(required, 10) × 100. The cap of 10 stops long "nice to have" lists from punishing everyone. It's deterministic and explainable — you can always see which skills matched and which are missing. Missing skills link to a YouTube course search. An optional Gemini "deep analysis" gives a fit score, strengths, gaps and eligibility notes from the full resume.

Scam filter

Regex red flags: asks for a fee or deposit, contact via WhatsApp/Telegram, "no interview", too-good pay claims, asks for ID/bank details, CV to a personal Gmail. One flag shows a warning; two or more hide the listing.

Assisted apply

The sheet has four steps: copy your details (name, email, phone, links); generate a cover letter and three answers (Gemini, instructed to use only resume facts); resume reminder and share button; open the employer's page. When you return, the app asks "Did you submit it?" — yes moves it to Applied and schedules a 7-day follow-up reminder through WorkManager.

A trust decision worth knowing: no "fake stars" flag Star counts can be bought, so I planned to flag repos with many stars but few watchers. The signal can't tell viral from fake, so the app shows the facts instead (stars, forks, created date, last update) plus a note that stars measure popularity, not quality or safety.

Data is stored in the rising_repos table (added by a database migration from version 1 to 2, so updating the app keeps bookmarks, the tracker and radar history). Repos that leave the list are kept for 30 days so their growth can be measured if they come back.

10Skills Radar — term discovery & verification

The most "AI-engineer" part of the app: an automatic system that finds newly emerging AI/ML/DS terms in live research text, decides whether they are genuinely new and growing using independent data, and explains each one using only quoted sources.

1. Discovery (no hardcoded terms)

  • Recent corpus: today's arXiv listings (cs.AI, cs.LG, cs.CL, cs.CV, stat.ML), a sample of AI/ML papers from the last 3 months (7 two-week windows × 120, via OpenAlex), news from the last 90 days, Hugging Face papers and GitHub repos. Job ads are excluded from mining (they're full of HR acronyms) and only counted later.
  • Acronyms are learned from text with the Schwartz & Hearst (2003) abbreviation algorithm: find "long form (SF)" patterns and match the short form's letters backwards through the preceding words. E.g. "Cache-Augmented Generation (CAG)" → CAG; it correctly ignores "2024 (USA)".
  • Phrases: 2–3-word title n-grams appearing in ≥4 documents.
  • Novelty ("lift"): rate in the recent corpus ÷ rate in a baseline of AI/ML papers from 6–18 months ago (6 windows × 200, via OpenAlex) plus older AI-blog posts. Only terms ≥3× more common now go forward. Both corpora count the term the same way (long form or acronym) — an early bug made "API" look new because the baseline only counted the long form.
  • Spelling variants with the same acronym (e.g. "RL with verifiable rewards" / "reinforcement learning with verifiable rewards") are merged, and the one the literature uses most is verified.

2. Verification (independent data)

The "took off" rule (OpenAlex publication history) For each term, OpenAlex returns the number of scholarly works per year containing the exact phrase.
baseline = median count of the years Y−10 … Y−5. If baseline > 30 works/yr, or > 2% of today's volume → established (rejected).
threshold = max(10, 5 × baseline). Took off = first year whose count ≥ threshold.
Accepted only if it took off in the last 3 years. New = took off this year or last; otherwise Rising.

  • Still growing: this year's annualised pace ≥ last year, or the 30-day rate ≥ 1.2× the prior 150-day rate.
  • Tools from job posts (e.g. LangGraph): mixed-case product names asked for by ≥3 employers, confirmed by two registries agreeing — a GitHub repo of that exact name with ≥1,000 stars and a PyPI or npm package of the same name that links back to that repo. "New" = first released under 2 years ago; otherwise the tool must be rising in job posts (share of the last 45 days ≥1.5× the older share). (Exact-name matching alone once matched "SaaS" to an unrelated repo.)

3. Explanation (quoted, never invented)

  • What it is: the Wikipedia summary if a page whose title contains the term exists (via Wikipedia search); otherwise the best definitional sentence from recent abstracts. Sentences where the term is the subject ("X is…", "X refers to…", "X, a …") score highest; papers describing their own system ("we propose…") are penalised; a readability score prefers plainer wording.
  • Where it's used: a sentence with an application cue ("used in", "applied to", "enables"…), excluding results sentences full of numbers and self-descriptions; an acronym glued into another name (VR-JEPA) doesn't count as the term.
  • Sources: the OpenAlex history link, recent arXiv papers, news, repos and job posts — top 3 shown on each card.
  • Optional plain-English rewrite by Gemini, kept only if it passes the grounding check (Section 12).

Persistence, budgets and "never guess"

  • Verified terms are stored permanently and shown instantly on launch; a background scan looks for new ones at most every 3 hours. Verified terms are re-checked every 3 days, rejected ones every 10 days; rejected ones are forgotten after 30 days.
  • When rules change, nothing is wiped: terms are labelled "re-checking", re-verified first, and removed only if they fail.
  • Without a key, OpenAlex gives a small daily budget shared per network IP (in testing, roughly 100 searches a day). The radar screens at most 20 new candidates per scan (plus pending re-checks) and spends at most 12 arXiv checks, supports an optional free personal key, and if OpenAlex's budget runs out it pauses and says so instead of guessing. arXiv calls are retried with backoff and fall back to OpenAlex.
  • A quality gate refuses to mine unless the baseline has ≥500 and the recent corpus ≥300 real arXiv papers (otherwise textbook terms look "new"); if not, it pauses and retries in ~3 hours.

11The on-device summarizer (the ML model)

Problem framing

Summaries must be ~50 words and must never contain false facts. Abstractive models (that write new text) hallucinate; small ones more so. So the task was framed as extractive summarization: score every sentence of the article and show the top sentences, verbatim, in original order. Faithfulness is guaranteed by construction — the model can only choose publisher sentences.

Why so small a model? 12Where LLMs are used (Gemini) — and how they're kept honest

The grounding check (TermMiner.grounded)

For every generated sentence: at least 70% of its content words (lightly stemmed) must appear in the sources, every number must appear verbatim, and every capitalised name must appear verbatim. Anything else is rejected. Unit tests prove it rejects an invented "40 times faster", an invented "invented at Microsoft" and an unsupported claim about hospitals.

Model handling: default gemini-2.5-flash-lite (free tier, cheap); if the model is retired (HTTP 404) the client lists available models and switches to the newest stable Flash-Lite model (or the newest Flash model); rate limits (429) pause AI features until the next refresh with a clear message.

13Background work, performance & memory

Refresh schedule

  • A WorkManager periodic job every 15 minutes (Android's minimum) when online: news every run, jobs at most hourly, radar at most every 3 hours. Android may delay it in Doze; a banner (and Settings) offers to allow unrestricted battery use so it keeps running.
  • Opening the app doesn't trigger a visible refresh: cached data shows instantly; a silent catch-up runs only if the worker hasn't refreshed in 20 minutes. The pull-to-refresh spinner appears only when the user pulls.

Three production problems and their fixes

1 · "isn't responding" (ANR)

Feed parsing, job parsing and term mining ran on the UI thread. Fix: all heavy work moved off the main thread; list filtering/clustering via flowOn(Default); jobs list uses a light projection (it was loading ~9 MB of descriptions on every change).

2 · App killed while scrolling (OOM)

Reproduced with a 256 MB heap: radar mining used +142 MB. Fix: don't mine job ads; index only acronym-like tokens; int-array postings; trimmed job text loaded via SQL substr; image cache capped at 12%. Now +77 MB with twice the data.

3 · CPU contention

News, jobs and radar all started at launch. Fix: HeavyWork: two dedicated threads at Android background priority (the scheduler always prefers the UI thread) + a mutex so memory-heavy phases run one at a time.

Proof

A live test swipes the real feed while a real refresh runs: 992 swipes, median 9 ms, p95 25 ms, max 501 ms (ANR threshold 5,000 ms). A crash recorder saves any crash so it can be copied from Settings.

Other optimisations

  • Streaming JSON decode for huge job boards; cheap tag-stripping instead of an HTML parser per RSS item.
  • The app root redraws only when theme/onboarding change, not on every settings write.
  • Lazy-list contentType hints for efficient recycling; radar sources decoded in the background.
  • arXiv requests are serialised at 1 per 3 s (arXiv's policy) with exponential backoff on failures.

21Interview questions — with answers

What is sudo, in one sentence?
An Android app that gives you verified tech and AI news in 50-word summaries made on the phone, a self-updating Skills Radar of genuinely new AI/ML terms, and resume-matched jobs with assisted apply.
Why did you build it?
To stay current in a fast-moving field without doom-scrolling or trusting unverified sources — and to make job hunting faster by matching roles to my real skills.
How do you make sure the app doesn't show fake or invented information?
Four layers: curated sources only; strict acceptance rules (real dates, link must be on the publisher's own site, no promos); extractive summaries that are verbatim publisher sentences; and a live truth audit that re-checks headlines, links, summaries, job pages, trending items and radar terms against the original sources. Generated text is optional, labelled and grounding-checked.
Why not just use an LLM to summarise?
LLMs can hallucinate, cost money and need a network. My use case needs ~50 faithful words, which sentence selection does perfectly. An LLM is offered as an option, constrained to the source text and labelled.
Describe your model.
An extractive sentence scorer: 20 hand-crafted features (position, length, title overlap, centroid similarity, TextRank, boilerplate flags…) into a 24-unit tanh MLP with a sigmoid output — 529 parameters. The top sentences are chosen within a 50-word budget with trigram blocking.
How did you get labels for training?
Oracle labelling: for each article I greedily selected the 1–3 sentences that maximise ROUGE-1 + ROUGE-2 against a human reference (CNN journalist highlights, or the publisher's own summary line for tech articles). Those sentences are positives.
How did you evaluate it, and is it good?
ROUGE F1 on held-out test sets against Lead, TextRank and the oracle ceiling. It beats Lead on both: 28.4 vs 27.4 ROUGE-1 on tech, 33.0 vs 31.6 on CNN. Lead is a notoriously strong baseline in news; the tech test set is small, so I describe that result as encouraging.
How did you avoid train/serve skew?
The feature code is one Kotlin file used by both the training job (run as a JVM test) and the app at inference. The trained weights are exported as JSON into the app's assets.
How does the Skills Radar decide a term is new?
Discovery: acronyms learned via the Schwartz–Hearst algorithm plus title phrases, kept if ≥3× more frequent than in papers from 6–18 months ago. Verification: OpenAlex's year-by-year publication counts must show the term took off within 3 years with almost no presence 5–10 years earlier; it must have ≥5 arXiv papers in the last 30 days and still be growing. It's then explained with a quoted source.
How do you handle a phrase that existed before with a different meaning?
I don't use "first appearance". I measure when volume surged above the phrase's own historical baseline (5× the median of years 5–10 ago). "Flow matching" had ~20 unrelated uses a year, then jumped to 315 in 2024 — so it's dated 2024.
What if your data sources are down or rate-limited?
The radar never guesses: it requires a minimum-size research corpus, retries arXiv with backoff (falling back to OpenAlex), detects OpenAlex budget exhaustion, and pauses with a visible message. Unchecked terms are neither passed nor rejected.
What was the hardest bug?
The app being killed while scrolling during a refresh. I reproduced it by running the radar's mining on real data with a 256 MB heap: +142 MB. I redesigned the mining (excluded job ads, acronym-only token index, int-array postings, SQL-trimmed text), serialised heavy jobs with a mutex on background-priority threads and capped the image cache — +77 MB with twice the data, and a test showing 992 swipes during a live refresh with a 25 ms p95.
How does background refresh work on Android?
WorkManager periodic work every 15 minutes (the minimum) with a network constraint. Doze can defer it, so the app requests a battery-optimisation exemption. Opening the app shows cached data and only catches up silently if the worker hasn't run recently.
Why Kotlin and Compose?
Native access to WorkManager, notifications, widgets and battery settings; performance for long lists; and the core logic runs unchanged in JVM tests. Compose made the animated, gradient-heavy UI straightforward.
How is the job match score computed?
Skills mentioned in the job (from an 82-skill vocabulary with aliases) are compared with the user's; score = matched ÷ min(required, 10). It's deterministic and explainable. An optional Gemini analysis adds a holistic view.
Why not auto-apply to jobs?
It violates job-site terms, breaks on CAPTCHAs and custom forms, and removes the user's review. Assisted apply gets 90% of the speed safely.
How do you keep the app responsive?
No heavy work on the UI thread; a dedicated two-thread dispatcher at background priority; a mutex so heavy phases don't overlap; flowOn for list transforms; light DB projections; capped image memory. Verified with a swipe-latency test during a live refresh.
How do you test something that depends on the live internet?
Pure logic is unit-tested offline with fixtures; UI is tested with Robolectric against a seeded in-memory database; and live, opt-in tests run the real pipelines and verify the output against the sources, reporting unverifiable cases instead of passing them.
How does "Rising on GitHub" know a repo is rising, not just big?
It ranks by stars gained per day, never by total stars: GitHub Trending's own weekly count, else the gain sudo measured between two of its checks, else a new repo's average since launch. Each card names its source. The list is renewed every 3rd morning only if a different set of repos makes the top 15.
What would you do with more time?
Instant removal of taken-down jobs, a learned skills vocabulary, a Play Store release with proper signing, encrypted key storage, more tech training data, and an Autofill service for job forms.
Is there anything hardcoded?
The list of trusted outlets and job boards (deliberately — it's the trust anchor), the 82-skill vocabulary for match scores, and thresholds (e.g. 3× lift, 3-year window). Terms, trends and explanations are all derived from live data.
